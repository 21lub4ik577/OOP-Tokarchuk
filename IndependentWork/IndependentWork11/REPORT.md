# Звіт з самостійної роботи №11

## Реалізація інвертованого індексу

Для пошуку документів у проєкті застосовано структуру інвертованого індексу. Слова вміщено у словник `Dictionary<string, HashSet<int>>`, де кожне ключове слово пов'язане з множиною ідентифікаторів документів. Самі документи зберігаються у словнику `Dictionary<int, Document>`, тому для кожного знайденого ID пошук об'єкта можна виконати за середньою складністю O(1).

Під час додавання документа його зміст розбивається на слова методом `TextProcessor.Tokenize`. Текст попередньо переводиться у нижній регістр, а розділові знаки та інші символи не включаються до ключових слів. Для кожного унікального слова відповідний документ додається до множини в індексі. Однак для повторення одного й того самого слова у тексті множина `HashSet<int>` не додає дублікатів, тому вказаний документ зберігатиметься для цього слова лише один раз.

Пошук одного слова повертає всі документи, для яких індекс містить відповідний ключ. Пошук за кількома словами створює множину документів для першого слова та послідовно застосовує до неї метод `IntersectWith`. У результаті залишаються лише ті документи, які містять усі запитувані слова. Пошук із логічною операцією OR будується методом `UnionWith`, що об'єднує множини документів для всіх знайдених ключових слів.

## Порівняння підходів до пошуку

Для порівняння було виконано лінійний пошук і пошук через інвертований індекс для наборів із 10, 100, 1000 і 10000 документів. Кожне вимірювання складалося зі 100 повторів пошуку слова `programming`. Середній час одного пошуку розраховувався у тиках таймера `Stopwatch`.

Обидва способи пошуку використовують метод `TextProcessor.Tokenize` і однакове приведення тексту до нижнього регістру. Це робить порівняння коректним, оскільки для перевірки рівності результатів лінійний пошук і пошук через індекс застосовують однакову нормалізацію. Для кожного набору кількість знайдених документів була однаковою в обох підходах.

| Кількість документів | Лінійний пошук, тиків | Інвертований індекс, тиків |
| -------------------: | --------------------: | -------------------------: |
|                   10 |                564,99 |                     622,26 |
|                  100 |               4050,52 |                     168,78 |
|                 1000 |              47070,38 |                    2258,76 |
|                10000 |             199851,02 |                   21051,95 |

На наборі з десяти документів лінійний пошук і індекс дали близькі результати, причому невелике перевищення часу пошуку через індекс пов'язане з накладними витратами виклику методу та виконанням множини операцій для малого обсягу даних. Уже на ста документах перевага індексного пошуку стає очевидною. При збільшенні набору до тисячі і десяти тисяч документів лінійний пошук зростає практично пропорційно кількості документів, тоді як пошук через словник залишається набагато швидшим.

## Інтерактивна перевірка

У консольному режимі було перевірено запит `programming language`. Обидва слова повинні одночасно міститися в документі, тому пошук повернув документи з ID 1, 2 і 3. Запит `c# async` повернув лише документ із ID 4, оскільки саме в ньому одночасно присутні обидва ключових слова.

Таким чином, у простій реалізації структура `Dictionary<string, HashSet<int>>` є доречною, бо словник забезпечує швидкий доступ до позицій документа за ключем, а множина дозволяє уникати повторів і виконувати операції перетину та об'єднання для AND/OR-пошуку. Основним обмеженням поточної моделі є відсутність ранжування, стемінгу та пошуку точної фрази. Крім того, пошук підтримує окремі слова й не враховує близькість або частоту слів у документі.
